# INC-001 — epilepc → ciphra migration was unusable in production

| | |
|---|---|
| **Reported** | 2026-08-07 by a migrating user, via support email |
| **Confirmed** | 2026-08-09 |
| **Severity** | High — the migration feature was 100% broken in production |
| **Data loss** | None. No user data was lost, corrupted, or exposed |
| **Resolved** | 2026-08-10 — root cause removed in production, verified end to end |
| **Status** | **RESOLVED.** One affected user pending manual unblock. Two follow-ups remain (session store, key-derive-once) |

## Summary

Every migration link epilepc minted pointed at `epilepc.ch`. That host does not
serve — it has issued a `301` to `www.epilepc.ch` since 2019. ciphra fetches the
export bundle cross-origin with `mode: 'cors'`, and the Fetch specification
requires *every* response in a redirect chain to pass the CORS check before the
browser will follow it. A `mod_rewrite` 301 carries no
`Access-Control-Allow-Origin`, so the browser aborted the request at the
redirect and never contacted the serving host.

The consequences of *where* it failed are the whole story:

- The request never reached PHP, so **nothing was logged** on epilepc.
- The migration token was never consumed, so **the database showed no attempt**.
- The browser reported a bare `TypeError: Failed to fetch`, which ciphra
  surfaced as "could not reach the source" — indistinguishable from an outage.

So a totally broken feature produced no server-side signal of any kind. It was
discovered only because a user wrote in.

## Impact

One user affected — and that is not reassuring, it is the finding. The
`migration_token` table contains seven rows in total: six from testing on
2026-06-11, and one from the reporter. **He was the first real migrant, and the
feature failed completely on first contact.**

Any user who had attempted a migration in this window would have failed
identically.

## What the user experienced

1. Minted a link on epilepc and opened it.
2. Registered a ciphra account *inside* the migration flow (the supported path).
3. Hit an error he could not recall — `migrate.error_fetch`, "Verbindung zur
   Quelle fehlgeschlagen". No data transferred.
4. Returned to epilepc to retry, could not get back in, and reported that his
   migration link was now unusable.

Step 4 was a **second, independent fault** (below). His phrase "Dein
Migrationslink für ciphra ist jetzt nicht mehr brauchbar" quotes the `<h1>` of
`migrate_link.html.twig` — he had gone back to that page and been met with an
error instead of the heading he remembered.

His own diagnosis — *"ich denke, dass die Kommunikation mit dem Server ein
temporäres Problem hatte"* — was reasonable and wrong, because our error copy
told him it was transient.

## Root cause

`epilepc/public/.htaccess`, unchanged since 2019-05-13:

```apache
RewriteCond %{HTTP_HOST} !^www.epilepc.ch$
RewriteRule ^(.*)$ https://www.epilepc.ch/$1 [R=301,L]
```

`CiphraMigrationController::start()` built the link from:

```php
$sourceHost = (string) ($_ENV['EPILEPC_ORIGIN'] ?? 'epilepc.ch');
```

The hardcoded fallback names the one host guaranteed not to serve. Whenever
`EPILEPC_ORIGIN` is absent from the environment — plausible on shared hosting
and across redeploys — every minted link is dead on arrival.

Measured on production, 2026-08-09:

```
$ curl -sI -H 'Origin: https://ciphra.ch' https://epilepc.ch/de/login
HTTP/2 301
location: https://www.epilepc.ch/de/login
server: cloudflare
(no access-control-* headers)
```

`www.epilepc.ch` was and is healthy: `204` with
`Access-Control-Allow-Origin: https://ciphra.ch`. **Only one value was wrong.**

## This was a recurrence, not a new failure

The same bug was hit during the first migration test on 2026-06-08. It is named
in the header comment of `frontend/src/lib/origin.ts`:

> that asymmetry caused the apex/www CORS bug during the first migration test
> (2026-06-08)

The response was `hostOf()`, added 2026-06-12, which normalises the *format* of
a source string (`https://host/` → `host`). It cannot change *which host* a
value names, so it could never have prevented this. Testing succeeded on
2026-06-11 (six tokens, one completed migration), which means the environment
was correct at that moment — and correctness that lives only in an unversioned
environment variable is correctness that will drift.

**The 2026-06-08 encounter was closed with a mitigation that addressed the shape
of the symptom rather than its cause.** That is the most important lesson here.

## Why nothing detected it

1. **The failure is invisible server-side.** No request, no log line, no
   database write. Monitoring cannot see it by design.
2. **There was no working end-to-end test.** `migrate-flow-typical.spec.ts`
   pointed at `localhost:5000`, but ciphra's CSP `connect-src` names only the
   production epilepc hosts, so the fetch was refused *inside the renderer*.
   The spec has been inert since CSP hardening (Track 3 P0 3.1) shipped, and it
   is gated behind `PLAYWRIGHT_RUN_MIGRATE` so nobody noticed it go quiet. The
   manual matrix in `api/fixtures/epilepc/README.md` is dead for the same reason.
3. **Dev cannot exercise the failing file.** The dev container sets
   `AllowOverride None`, so `.htaccess` — the file that caused the incident — is
   never evaluated locally.
4. **The error copy blamed the network.** "Verbindung zur Quelle fehlgeschlagen"
   reads as transient, so the natural user response is to retry rather than
   report.

## Second defect: the export cannot finish for heavy accounts

Found while building the reproduction. `EpilepcBundleSerializer` reads two
`@Encrypted` fields per record, and `doctrine-encrypt-bundle` derives a key per
field, so cost is linear and steep.

**Measured: 1365 records → 193.5 seconds** (~142 ms/record).

Cloudflare's free tier terminates an origin request at 100 s with a `524`.
A long-tenured account therefore *cannot* complete an export through the CDN.
`set_time_limit(300)` in `export()` protects PHP but has no authority over the
edge.

This mattered urgently, because fixing the redirect alone would have exposed it
immediately — to exactly the long-tenured users most likely to migrate.

## Third defect: a failed export destroyed the user's only link

`export()` stamped `used_at` *before* serialising, with the rationale that a
retry should require a fresh token. In practice that traded a rare abuse case
for a common self-inflicted one: any post-stamp failure — serializer exception,
OOM, gateway timeout — permanently spent the link while delivering nothing, and
the user cannot mint a replacement without getting back into their account.

Not triggered by this incident (the request never arrived), but it would have
been by the 100 s timeout above.

## Evidence

**`migration_token` — production, the reporter's row:**

| used_at | migration_completed_at | ip_first_seen |
|---|---|---|
| NULL | NULL | NULL |

`ip_first_seen` is written inside `export()` immediately after the single-use
stamp. NULL proves the controller never executed — which rules out every
server-side theory (timeout, 500, token burn) and leaves only "the request
never arrived".

**Reproduction output** (`scripts/repro-inc-001.sh`), byte-for-byte match:

```
used_at                migration_completed_at ip_first_seen
NULL                   NULL                   NULL            ← apex  (the incident)
2026-08-09 21:43:52    2026-08-09 21:44:06    172.22.0.1      ← www   (a working migration)
```

Only the source host differs between the two runs.

**`prod.log`** — see the ops section; it contains no export entry at all,
consistent with the request never reaching Symfony. (Monolog runs
`fingers_crossed: action_level: error`, so a *successful* request logs nothing
either — absence alone is not proof, but combined with the NULL row it is.)

## Remediation

### Shipped (deployed 2026-08-10)

| Change | Effect |
|---|---|
| `public/.htaccess` — exempt `/api/ciphra-export` + `/api/migration-complete` from the redirect | Removes the root cause. Also un-breaks `direct.epilepc.ch`, the CDN-bypass host already in DNS and ciphra's CSP but swallowed by the same rule — which addresses the 193 s export budget |
| `start()` — resolve `MIGRATION_EXPORT_HOST` → `EPILEPC_ORIGIN` → **request host** | A link can no longer be minted against a host that does not serve. No hardcoded constant to drift |
| `export()` — consume the token only on successful serialisation | A failed export no longer destroys the link. IP still recorded immediately for forensics |
| `fetchBundle` — `www.` fallback + `resolvedBase` threaded into `signalMigrationComplete` | A misconfigured source self-heals; the completion signal follows the host that actually answered |
| `runImport` — `ensureEpisodeTypes` + checked blueprint save | A migrant pushed through `/setup` after a failed attempt no longer imports data that renders as nothing. Additive; never replaces existing config (cf. the 2026-06-20 medication data-loss incident) |
| `migrate-flow-typical.spec.ts` — repointed, CSP + LNA handled | The pre-existing e2e test executes again |

### Rejected: adding CORS headers to the 301

Tested, and it is **worse than the current bug**. The redirect is then followed,
so the request reaches PHP and the token *is* consumed — but a cross-origin
redirect taints the follow-up request's `Origin` to `null`, epilepc echoes its
configured `CIPHRA_ORIGIN` instead, and the browser discards the response
anyway. Net: same error, link now spent, nothing delivered. Making it work would
require `Access-Control-Allow-Origin: null`, which every sandboxed or opaque
origin also satisfies. Pinned by a test so nobody reaches for it later.

## The first `.htaccess` fix was wrong

Worth recording in full, because it is the most instructive part of the
incident and it very nearly shipped unnoticed a second time.

The original exemption was written against `%{REQUEST_URI}`:

```apache
RewriteCond %{REQUEST_URI} !^/api/(ciphra-export|migration-complete)/ [NC]
```

The Symfony front controller further down the same file rewrites everything to
`index.php`, and that makes Apache **re-run the entire ruleset**. On the second
pass `%{REQUEST_URI}` is already `/index.php`, the exemption no longer matches,
and the canonicalisation fires after all — now discarding the path as well:

```
before the fix:  location: https://www.epilepc.ch/api/ciphra-export/probe
after  the fix:  location: https://www.epilepc.ch/index.php     ← still broken
```

The behaviour *changed*, which made the deploy look successful. Only the
production probe showed it was still redirecting.

`%{THE_REQUEST}` is the verbatim request line (`GET /api/… HTTP/1.1`) and is
never rewritten, so it stays true on every pass.

**Why it took production to find out — again.** `public/.htaccess` could not be
tested anywhere else: the dev container ran `AllowOverride None`, so Apache
ignored the file entirely. The single file responsible for the incident was the
one file the local stack could not execute. That is now closed:

- dev container runs `AllowOverride All`
- the canonicalisation rule skips loopback hosts, so the local stack still works
  with the rule active (production `HTTP_HOST` is never loopback, so this cannot
  weaken anything there)
- `epilepc/scripts/test-htaccess.sh` pins the matrix, including the `/index.php`
  path-loss signature of this specific bug

Verified by reverting to the broken condition locally and watching the test fail
with the exact production symptom.

## Resolution

Verified in production on 2026-08-10 07:40 UTC
(`scripts/verify-migration-prod.sh`, `.inc001/before.txt` → `after2.txt`):

| Host | Before | After |
|---|---|---|
| `epilepc.ch` | 301, no CORS · browser: `Failed to fetch` | **204 + correct CORS · browser: 404** |
| `direct.epilepc.ch` | 301, no CORS · browser: `Failed to fetch` | **204 + correct CORS · browser: 404** |
| `www.epilepc.ch` | healthy | healthy |

A `404` for a deliberately invalid token is the healthy answer: it proves the
request reached PHP, which then rejected a token we invented.

Note the two independent layers of protection now in place. ciphra's `www.`
fallback resolved the user-facing failure at 06:49, an hour before the epilepc
root-cause fix landed — an already-issued `source=epilepc.ch` link works either
way.

## Unblocking the affected user

No deploy is required: `www.epilepc.ch` already serves correctly and his token
was never consumed.

```sql
SELECT mt.token, mt.expires_at, mt.used_at
  FROM migration_token mt JOIN user u ON u.id = mt.user_id
 WHERE u.email = '<email>' AND mt.used_at IS NULL AND mt.expires_at > NOW()
 ORDER BY mt.created_at DESC LIMIT 1;
```

```bash
scripts/unblock-migrant.sh <token> www.epilepc.ch
```

Reply template: `docs/incidents/INC-001-reply-de.md`.

Two cautions. Tell him **not to run the ciphra setup wizard first** — his
account has no blueprint, the dashboard pushes exactly those users into
`/setup`, and a non-epilepsy blueprint chosen there changes what the import
looks like. And note that `unblock-migrant.sh` never issues a `GET` to the
export URL: on current production that would spend his link and discard the
bundle.

## Prevention

| Mechanism | Catches |
|---|---|
| `scripts/verify-migration-origin.sh` | A source host that redirects or has wrong CORS. Free `OPTIONS` probe — `export()` answers OPTIONS before the rate limiter and before any token lookup. Run before any deploy touching origins, DNS, or the CDN |
| `frontend/e2e/migrate-apex-redirect.spec.ts` | Five cases: the incident itself, a working control, the fix, the rejected alternative, and the token-burn behaviour |
| Export-duration budget assertion | The 100 s CDN ceiling, so the 193 s problem cannot regress silently |
| `scripts/repro-inc-001.sh` | One-command full-stack reconstruction |

## Follow-ups (not done)

- **`app_locales` has no leading slashes** (`services.yaml:8`), so
  `^(%app_locales%)/app` compiles to `^(en|it|fr|de)/app` and never matches
  `/de/app/...`. All three `access_control` rules are dead. Authorisation still
  holds — all nine controllers carry `@IsGranted` — but the firewall-level
  redirect-to-login is gone, so anonymous users reach argument resolution and
  the non-nullable `UserInterface $user` throws a **500 instead of a login
  redirect**. This is what the reporter hit on 2026-08-08.
- **No GET route for the migrate-link page.** `app_ciphra_migrate_start` is
  POST-only and renders the link as its POST response, so any revisit or reload
  yields a raw 405. Split it: GET renders, POST mints.
- **Key-derive-once refactor** for `doctrine-encrypt-bundle`, the real fix for
  the 142 ms/record export cost. Long-standing P2, now with a number attached.
- ~~Dev/prod divergence on `.htaccess`~~ — closed 2026-08-10, see above.
- **No alerting on migration outcomes.** A migration that fails in the browser
  is invisible. Consider having ciphra report failed migration attempts.

## Ops: epilepc session store (separate P0, still open)

`prod.log`, 2026-08-07 23:03:56 — one session, cascading:

```
open(/var/cache/php-sessions/sess_...) failed: Permission denied (13)
→ session_start(): Failed to read session data
→ RuntimeException: "Failed to start the session."
→ "Exception thrown when handling an exception" ×2
```

The error page dies on the same fault, so the user gets a bare 500. Without a
session, login cannot persist and `isCsrfTokenValid('migrate_start')` cannot
pass — so the migrate-link form is unusable even when reachable. This is why the
reporter could not help himself.

Both log clusters fall between 23:00 and 23:40, which suggests a nightly job
running as root leaving root-owned files in `/var/cache/php-sessions`. Fix the
ownership *and* find what re-breaks it, or it returns.
